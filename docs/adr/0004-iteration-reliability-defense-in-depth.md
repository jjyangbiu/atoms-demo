# ADR 0004：迭代可靠性——多层防线

- 状态：已接受（2026-09-15，经需求拷问会确认）

## 背景

项目经过多轮对话后，增量修改不可靠：用户要求改 A 处，结果 B、C 处也被改掉。根因不是单点 bug，而是"模型凭记忆整体重写"这一默认行为在长对话里被多种因素放大。拷问会归纳出五种失败模式：

- (a) **整体覆写漂移**：`write_file` 可覆写已有文件，模型倾向于重写整个文件，顺手改掉无关区域。
- (b) **陈旧记忆匹配失败**：模型凭上一轮记忆里的旧内容做 `edit_file`，文件已变，`old_text` 匹配不上或匹配到错位。
- (c) **窗口截断失忆**：对话只喂最近 10 轮，更早的改动意图被截掉，模型不知道项目已演进到哪。
- (d) **多处匹配打偏**：`old_text` 在文件中出现多次，替换打到了非目标那一处。
- (e) **指令模糊泛化**：用户指令笼统，模型自行扩大改动范围。

工程师模式与团队模式都发起多轮对话，两者都受影响。增量修改的语义定为**区域级**（只动受影响的区域），而非文件级或全量重写。

## 决策

不依赖任何单层，而是叠六道相互独立的防线；前四层是工具/提示词层的**预防硬闸**，第五层补上下文，第六层是**事后检测安全网**。

1. **`edit_file` 分层定位**（防 b、d）：替换按四级降级——精确且唯一则改；精确但多处命中则报错并要求补上下文（不猜）；精确未命中则尝试忽略空白/缩进的模糊匹配（唯一命中才改）；仍不中则报错并指引"先 `read_file` 逐字复制 `old_text`"。杜绝"替换第一处"的打偏。
2. **`write_file` 禁改已有文件**（防 a）：`write_file` 只用于新建；目标已存在则报错，强制走 `edit_file`。系统提示规则收紧为"修改已有文件只能 `edit_file`，且只动受影响区域、`old_text` 必须唯一、不得凭记忆"。
3. **read-before-write 强制**（防 b）：沙箱每轮生成新建实例并记录本轮已读文件；`edit_file` 前该文件必须已被 `read_file`（或本轮 `write_file` 刚建），否则报错。物理上禁止凭记忆改文件。
4. **文件摘要注入**（防 b、e）：系统提示附每个文件的路径 + 行数 + 内容哈希前 8 位。哈希让模型识别"记忆已过时"，触发强制 `read_file`。
5. **迭代日志**（防 c）：`Project.iteration_log`（JSON 列）由系统在每轮**成功**生成后追加一条 `{round, user_text, files}`，并注入后续轮的系统提示。它不随对话窗口截断，是历轮改动的紧凑摘要——弥补窗口截断的失忆，且比喂全量历史更省 token、语义更聚焦。
6. **diff 面板**（检测安全网）：新增 `GET /snapshots/{id}/diff` 端点，比较某快照与其前一版，返回文件级差异（added/modified/removed + 旧新内容）；前端 `DiffPanel.vue` 以"文件级列表 + 展开看 Monaco diff"呈现。用户在每轮后核对"只改了该改的文件"，配合既有的**项目级回滚**兜底。

## 被否决的替代方案

- **只靠提示词约束、不加工具层硬闸**：提示词是建议性的，长对话里模型必然漂移；read-before-write、`write_file` 限制是物理强制，不依赖模型自觉。
- **扩大/取消对话窗口代替迭代日志**：喂全量历史 token 与成本爆炸，且原始历史 ≠ 蒸馏后的"改了什么"；迭代日志是不截断的紧凑改动摘要，专治失忆。
- **行级 diff 粒度 / 自动 diff 回滚**：拷问会选定文件级列表 + 展开；行级自动回滚过于激进且复杂，粗粒度的项目级回滚已是现成的安全阀。
- **给团队模式单独的迭代日志机制**：迭代日志是项目级、按"用户对话轮"记录的统一机制，不另起炉灶。团队工单执行传 `record_iteration=False` **既不读也不写**迭代日志——工单指令（"现在执行工单 N…"）是内部编排而非用户发言，记进去会把编排指令当"用户说"注入后续工单提示、破坏工单隔离；工单阶段本就有自己的清单边界上下文。这是对"团队模式不做特殊处理"的作用域澄清，而非新增分支。
- **`edit_file` 用行号定位**：一轮内文件多次改动会让行号漂移；精确文本 + 空白模糊匹配更稳健且自校验。
- **`write_file` 保留 upsert 覆写语义**：那正是失败模式 (a)；禁掉它才能逼出外科手术式的局部改。

## 后果

- 正面：增量修改变得局部化、可核验；多道独立闸门意味着任一层失效都不会造成静默腐化；迭代日志跨窗口存活；diff 面板给用户事后检测手段，与项目级回滚形成"预防 + 检测 + 兜底"闭环。
- 代价：每次改动前须先 `read_file`（多一次工具调用，略增延迟与 token）；`write_file` 不能再覆写，依赖整体重写的模型脚本须改走 `edit_file`（本仓 9 处集成测试的迭代轮已相应补 `read_file` 步骤）；`Project` 表新增 JSON 列，靠 `ensure_schema` 手工补列（项目无 Alembic）；系统提示随文件数与迭代轮数增长（token 成本随项目规模上升）；diff 端点每次请求从磁盘读快照留档。
- 有意偏离、易被误"修复"处：`write_file` 拒绝已有文件、`edit_file` 强制先读、团队工单不计迭代日志——三者都是刻意的硬约束，非缺陷。
