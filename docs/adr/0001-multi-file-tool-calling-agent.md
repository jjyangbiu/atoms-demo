# ADR 0001：多文件项目 + 工具调用式智能体

- 状态：已接受（2026-08-30，经需求拷问会确认）

## 背景

本平台的核心是"智能体驱动的应用生成"。生成产物的形态与智能体的文件操作机制是最难回头的两个基础决策：

- 产物形态可选：单文件 HTML（最简单）、多文件项目（接近 Atoms 真实体验）、全栈应用（含后端，复杂度最高）。
- 文件操作机制可选：结构化 JSON 全量输出、工具调用（function calling）循环、混合方案。

## 决策

1. **产物形态采用多文件项目**：项目建模为"一组文件"，智能体可创建/修改多个文件（index.html + 独立 js/css 等）。
2. **文件操作采用工具调用式智能体**：智能体通过 `write_file` / `edit_file` / `read_file` 等工具多轮循环完成生成与迭代修改，基于 LangChain tool calling 实现。
3. 生成物限定**纯前端 + CDN、无构建步骤**（Tailwind CDN、ECharts 等），保证静态托管预览即开即用。

## 被否决的替代方案

- **单文件 HTML**：预览零成本、可靠性高，但与 Atoms 体验差距大；多轮迭代时单文件膨胀导致 token 浪费。保留余地：数据模型按"项目=一组文件"设计，单文件场景天然兼容。
- **结构化 JSON 全量输出**：格式可控、容错好做，但每轮迭代需重传全量文件，token 消耗大，且缺乏"智能体自主工作"的演示叙事。
- **允许构建步骤的项目（如 Vite 工程）**：需要服务器端沙箱构建，超时/依赖安装风险在 1~2 周工期内不可控。

## 后果

- 正面：交互与叙事最接近 Atoms；迭代修改是增量的，token 经济；评审时过程展示（"正在写入 index.html"）有说服力。
- 代价：实现依赖 MiniMax-M3 的 function calling 稳定性，需要做好格式兜底与失败重试；多文件落盘托管需要独立的静态服务路径与路径穿越防护。
