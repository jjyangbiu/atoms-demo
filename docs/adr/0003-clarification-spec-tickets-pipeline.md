# ADR 0003：需求澄清与多智能体生成流水线（团队模式重定义）

- 状态：已接受（2026-08-31，经需求拷问会确认）

## 背景

新建项目后用户发送一句话需求，智能体即一次性生成全部代码，模糊需求靠模型脑补，产物与用户预期偏差大。mattpocock/skills 的 grilling（分轮拷问直至无未决问题）、to-spec（把共识沉淀为规格）、to-tickets（纵向切片 + 阻塞依赖）提供了成熟的"彻底澄清 → 拆解 → 分步执行"范式。同时，团队模式的最初实现（产品经理智能体产 PRD）已偏离其"多智能体协作"本意，需要重定义。

## 决策

1. **流水线分层定位**：
   - 工程师模式（保持快速）：需求澄清 → 需求共识确认门 → 工程师一次性生成。
   - 团队模式（多智能体全流程）：需求澄清 → 需求规格确认门 → 工单清单确认门 → 工程师按检查点串行执行。
   - 团队模式旧"产 PRD"流程退役，由需求规格承接其职责；历史项目的 PRD 数据与只读路径保留兼容。
2. **澄清采用改写后的 grilling 方法论**（提示词层面，非原文照搬）：每轮把所有会实质影响生成结果的未决问题合并为一条消息、每题附推荐答案；无未决问题即收敛；用户随时可说"直接生成"跳过。澄清智能体唯一工具是 `start_build(requirements_summary)`，物理上无法提前写代码。不设澄清轮数硬上限。
3. **检查点串行执行**：每个工单执行完成形成一个检查点快照（融入现有 Snapshot 体系，可预览、可回滚）；工单失败从该工单起点重试；回滚到某检查点后，其后工单重置为未完成，由用户手动触发"继续执行"。执行期不可重新澄清、不可重新拆单（推翻重来只能新建项目）。
4. **限额语义变更**：一个新建项目的首建流水线整体只占 1 个生成名额（工程师模式覆盖澄清到生成完，团队模式覆盖澄清到全部工单执行完），断线重连与失败重试不重复占用；生成完成后的迭代消息仍按现行规则每次计数。这是对工单 0011"调了模型就计数"原则在首建场景的有意偏离，防滥用约束见第 3 条。
5. **持久化形态**：共识/规格及其确认沿用消息 `kind` 模式（`consensus`/`consensus_confirm`、`spec`/`spec_confirm`）；工单是唯一的新表（项目、序号、标题、交付内容、阻塞依赖、状态、检查点快照引用）；阶段状态沿用 `_prd_state` 的"从消息历史推导"风格，不加项目表字段。

## 被否决的替代方案

- **澄清完成自动开工（无确认门）**：一句话需求经多轮问答后摘要写歪的概率不低，确认门是廉价保险，且复用既有卡片交互。
- **新旧流程机械叠加（共识 + spec + tickets + PRD 并存五类文档）**：越叠越臃肿；团队模式的新流水线本身就是其多智能体本意的完整实现，PRD 应让位而非并列。
- **澄清轮数硬上限（3 轮强制带假设收敛）**：违背 grilling"问完为止"的方法论，会在关键问题处被强行截断；防无限问答的闸门在用户逃生门，不在计数器。
- **工单一次性执行（无检查点）**：工单的价值正在于生成可控、可中断、可恢复；单次工具循环跑完则失败重来、用户无法干预，拆单降格为内部细节。
- **澄清调用逐次计限额**：流水线语境下一个应用会吃掉近十个名额，限额数字快速见底，与"一次名额管到底"的体验目标冲突。

## 后果

- 正面：生成前需求彻底澄清，产物符合预期；团队模式名副其实的"多智能体全流程"；执行可中断、可恢复、可回滚，与快照/迭代体系一致。
- 代价：团队模式用户生成前需完成最多三次交互（澄清问答、确认规格、确认工单）；长流水线占用名额的持有与释放逻辑比逐次计数复杂；PRD 相关代码成为遗留路径，需长期兼容历史项目；团队模式首建耗时显著增加（多阶段串行模型调用）。
